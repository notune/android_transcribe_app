# Swarm Planning Gate: OVI-001

## Вывод

Параллельное исполнение для этой задачи не даёт выигрыша. Работа идёт одним
потоком записи, потому что все изменённые файлы связаны общей моделью
состояния диктовки: сессия, поле, исходный текст и признак отмены. Второй
писатель в тех же файлах создал бы конфликт и риск повторной вставки.

Параллельно можно только читать и проверять, и это вынесено в независимую
проверку после фиксации SHA.

## DAG

```
подготовка документов
        |
        v
   один коммит (SHA)
        |
        +--> тесты (JVM)
        +--> сборка APK
        +--> lint
        +--> снимок безопасности
        |
        v
  независимая проверка (codex, отдельный контекст)
        |
        v
   приёмка, отчёт
```

## Рабочие области

| Область | Файлы | Владелец |
|---|---|---|
| Логика и клиент | `PostProcessingLogic`, `OpenAiCompatibleClient`, `PostProcessor`, `SecretStore`, `EditorTarget` | инженер, один поток |
| Три пути ввода | `RustInputMethodService`, `RecognizeActivity`, `VoiceRecognitionService` | инженер, один поток |
| Интерфейс | `activity_main.xml`, `strings.xml` и переводы | инженер, один поток |
| Документы | `docs/aek/*`, `docs/*` | инженер, один поток |

Общий ресурс один: рабочее дерево Git. Второй писатель запрещён до коммита.

## Почему не параллелим

- `RustInputMethodService` и `RecognizeActivity` делят `PostProcessor`
  и правила отмены. Раздельная правка сломала бы контракт.
- Строки лежат в семи файлах перевода. Правка в двух потоках даёт конфликт
  слияния.
- Сборка и тесты используют один каталог `app/build`.

## Проверяющий

Проверяющий работает в отдельном контексте на том же SHA, без права менять
код. Его задача описана в `.agentic-kit/evidence/OVI-001/review-brief.md`.
Он идёт через другого провайдера, чем исполнитель.

## Интеграция

Ответственный за интеграцию один: ведущая сессия. Она делает коммит,
запускает проверки, импортирует результаты проверяющего и принимает решение.
