# Harness Discovery & Assignment

**Роли:** Orchestrator (ответственный), PM/BA (диалог), Architect (оценка пригодности), Security (границы доступа).

**Триггер:** создание проекта; подключение к существующему; изменение доступных харнессов/моделей, бюджета или политики данных. Не выполняй повторно без существенной причины.

## Обязательные действия

1. **Discover:** безопасно проверь CLI/версии/инструменты/MCP/skills. Секреты не читай; настройки не меняй.
2. **Differentiate:** различай обнаруженную установку, подтверждение запуска пользователем и запуск, проверенный в этой среде. Не считай наличие CLI доказательством модели, effort или прав.
3. **Ask:** только если нужно, уточни согласие на провайдеров и передачу данных, бюджет, предпочтения, запрещённые действия и параллелизм.
4. **Assess:** оцени качество по контрольным задачам (если разрешены), доступные инструменты, сложность, стоимость, ограничения и риски. Не назначай модель по названию.
5. **Propose:** покажи таблицу `роль → primary harness/model/effort → tools/skills → data/permissions → fallback` со статусом проверок.
6. **Approve:** получи явное согласование существенных маршрутов и доступа к данным. Не подделывай подтверждение.
7. **Persist:** сохрани реестр, матрицу и источник согласования. Для standard/critical используй `routes_confirmed` перед реализацией.
8. **Operate:** применяй только согласованный primary/fallback, пересматривай при изменении обстоятельств. Не утверждай, что AEK запускает все харнессы автоматически.

**Результат:** сохраняемая матрица назначений, статус подтверждений и список невыясненных ограничений. Правила: `docs/HARNESS_ROUTING.md`.
