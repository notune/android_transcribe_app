# Обновление установленного AEK

Штатная команда `upgrade` доступна начиная с AEK `1.7.0-rc.1`. Она обновляет стандарт внутри существующего проекта, не переустанавливая проект и не заменяя его пользовательские изменения.

## Из T3 Code, Codex, OpenCode или Pi

Открой корень проекта, в который уже установлен AEK, и отправь агенту:

> Обнови Agentic Engineering Kit из приватного репозитория https://github.com/kelvmg/agentic-engineering-kit. Прочитай `docs/UPGRADE.md` в новой версии, получи её через действующую авторизацию GitHub в отдельную папку вне проекта, зафиксируй commit SHA и состояние Git. Сначала выполни `python3 tools/aek.py upgrade --target <путь к проекту> --diff` без `--apply`. Покажи изменения, конфликты, текущие профили и `plan_id`. После моего согласия запусти обновление с точным `--plan-id`. Сохрани `backup_id` и проверь `VERSION` и зарегистрированные скиллы. Не меняй код приложения, OpenSpec, CI, мои инструкции и данные задач. Затем отдельно предложи подключить `codebase-audit`.

Нужны Git, Python 3.10+ и доступ к приватному репозиторию через существующую авторизацию. Не передавай токены в чат. Не запускай команды вида `curl | bash`.


## Единое обновление окружения

Команда `/aek_update` (Codex `$aek-update`) использует `aek.py update`. В её план включаются кит, активированные навыки и явно зарегистрированные команды/инструменты. Управляемые глобальные команды могут обновляться в том же плане после регистрации их области. Подробности и ограничения кандидатов: [COMPONENTS.md](COMPONENTS.md).

Ниже описан низкоуровневый `upgrade`: он меняет только кит и активированные проектные навыки. Он остаётся доступным для целевого обновления этого компонента.

## Из терминала

Все команды ниже запускаются из **отдельного клона новой версии AEK**, расположенного **вне целевого проекта**. Не используй старый `.agentic-kit/tools/aek.py` для обновления.

```bash
cd /path/to/reviewed-aek-clone
git rev-parse HEAD
PROJECT="/absolute/path/to/project"

# Предварительный просмотр. Ничего не меняет
python3 tools/aek.py upgrade --target "$PROJECT" --diff
```

Результат содержит `from_version`, `to_version`, список действий `operations`, сохранённые профили `active_profiles`, конфликты `conflicts` и идентификатор `plan_id`. Флаг `--diff` показывает сравнение текстовых файлов AEK, изменяемых при обновлении.

После просмотра и явного согласования подставь выданный идентификатор:

```bash
python3 tools/aek.py upgrade --target "$PROJECT" \
  --apply --plan-id PLAN_ID_ИЗ_ПРЕДВАРИТЕЛЬНОГО_ПРОСМОТРА
```

Если текущие файлы или исходная версия AEK изменились между просмотром и применением, старый `plan_id` не подойдёт. Сначала повтори просмотр. При любом конфликте запись блокируется.

После успешного применения команда сообщает `backup_id`. Резервные копии находятся в `.agentic-kit/upgrade-history/<backup_id>/`. Историю не удаляй, пока не убедишься в работоспособности новой версии.

## Точная идентичность исходника

Новые установки и обновления сохраняют `source_identity` в `.agentic-kit/install-manifest.json`: версию, SHA256 фактически поставляемых файлов и их количество. План `upgrade` показывает `from_source_identity` и `to_source_identity`, поэтому две сборки с одинаковым `VERSION` можно различить по содержимому.

`git_commit` и `git_tree` записываются только для чистого корня Git-репозитория, где проверен локальный исходник. При изменённых или неотслеживаемых файлах `source_dirty: true`, а точные Git-поля остаются `null`. Для источника без доступной Git-истории или вложенной копии кита эти поля и `source_dirty` остаются `null`; контрольная сумма содержимого сохраняется. Это не подтверждение издателя и не утверждение, что локальные файлы совпадают с удалённой веткой.

Старые манифесты без `source_identity` по-прежнему поддерживаются. В инвентаре их происхождение обозначается `legacy_unknown`; недостающий commit не подставляется из текущего клона. Откат возвращает прежний манифест вместе с его исходными сведениями.

## Что обновляется

- Управляемые файлы из старого `.agentic-kit/install-manifest.json`. Контрольные суммы SHA256 позволяют обнаружить ручные изменения.
- Только **ранее зарегистрированные** базовые и дополнительные скиллы в `.agents/skills/`; уже включённые профили сохраняются. Новые необязательные профили не подключаются автоматически.
- Манифест установленного AEK с версией и перечнем управляемых файлов.

## Что сохраняется

- Исходный код, `AGENTS.md`, `CLAUDE.md`, пользовательские инструкции, OpenSpec, CI и `t3.json`.
- `.agentic-kit/tasks/`, подтверждения выполнения задач, пользовательские файлы и ранее созданный `.agentic-kit/ADOPTION.md`.
- Сторонние скиллы и программы, не управляемые AEK.

Команда не устанавливает библиотеки, не запускает агентов, не меняет Git-ветки и не устраняет противоречия автоматически. Для первоначального подключения проекта по-прежнему используется `install`; для уже подключённого проекта используй **`upgrade`, а не повторный `install --apply`**.

## Откат

Если обновление завершилось успешно, но его нужно отменить:

```bash
python3 tools/aek.py rollback --target "$PROJECT" --id BACKUP_ID
# После просмотра и согласования:
python3 tools/aek.py rollback --target "$PROJECT" \
  --id BACKUP_ID --apply --plan-id PLAN_ID_ОТКАТА
```

Откат запрещён, если файлы, изменённые предыдущим обновлением, были дополнительно отредактированы. Это защищает новые пользовательские изменения. Сначала разреши конфликт вручную.

**Граница гарантии:** обычная ошибка записи запускает восстановление уже затронутых файлов. При аварийном завершении процесса или выключении машины возможна частичная установка; исходные копии остаются в истории. Перед крупным обновлением рекомендуется отдельная точка восстановления в Git или резервная копия.

## Изменение порядка проверки при переходе на AEK 2.0

Управляемые файлы стандарта обновляются без изменения исходного кода продукта, однако правила проверки задач стали строже. Старые произвольные файлы `tests` и `runtime_smoke` больше не считаются доказательством запуска команды. Требуется заново выполнить соответствующие тесты через `record --run` для актуального коммита.

Для UI-задач добавлены `browser_capability` до проектирования и `visual_qa` перед завершением, в том числе для `lite`. При применении новых требований к уже начатой задаче сохрани прежние доказательства и согласуй план их актуализации; не заменяй их фиктивными данными. Новые инструменты браузера и UI-библиотеки не устанавливаются автоматически. Для строгого контроля слияния требуется отдельная настройка проверенного CI.

## Проверка после обновления

Проверь `.agentic-kit/VERSION`, версию и список управляемых файлов в `.agentic-kit/install-manifest.json`. Если нужно включить новый профиль `codebase-audit`, сделай это отдельным согласованным шагом:

```bash
python3 tools/aek_activate.py plan --target "$PROJECT" --profile codebase-audit
# После проверки и согласования:
python3 tools/aek_activate.py apply --target "$PROJECT" --profile codebase-audit --plan-id PLAN_ID
python3 tools/aek_activate.py check --target "$PROJECT" --profile codebase-audit
```

Проверь целостность установки и ранее зафиксированное окружение:

```bash
python3 tools/aek.py doctor --target "$PROJECT"
python3 tools/aek.py environment check --target "$PROJECT"
```

После обновления прежний lock ожидаемо может не совпадать с новым состоянием. Просмотри `environment plan --target "$PROJECT"` и зафиксируй проверенный результат через `environment apply --target "$PROJECT" --plan-id PLAN_ID`. Если lock ещё не создавался, используй ту же последовательность. Она сохраняет локальный инвентарь и ничего не устанавливает. Не принимай изменённые управляемые файлы или незавершённое восстановление как новое штатное состояние. Подробности: [COMPONENTS.md](COMPONENTS.md#фиксация-и-проверка-окружения).

Создай новую сессию агента в T3 Code. Проверка файлов не доказывает, что провайдер уже загрузил новые скиллы. Для первого испытания `codebase-audit` разумно выбрать `quick` без изменения кода приложения.

## Граница поручения и новые наблюдения проверок

После обновления не меняй исторические done/cancelled. Для открытых задач отдельно
проверь `execution_boundary` и требования `isolation` в назначениях. Отсутствие этих
полей не является разрешением продолжить до done или использовать общий каталог.
Зафиксируй действующее поручение через `boundary`, а новые назначения с требованиями
изоляции через `review assign`. Не выдавай согласование агента за сообщение человека.
Подробности: [PROCESSES.md](PROCESSES.md), [INDEPENDENT_REVIEWS.md](INDEPENDENT_REVIEWS.md).

Сохраняй прежние входные файлы и журналы. Новые импорты архивируются внутри evidence;
старые перезаписанные ответы невозможно восстановить из одного хеша. Не объявляй
их сохранёнными без фактического источника. При недоступности результата зафиксируй
препятствие и получи новую реальную проверку по установленному процессу.
