# Управление процессом и ограничения enforcement

**Workflow Enforcement** означает, что при исполнении задачи используется зафиксированный этап, обязательные артефакты, оценки рисков, план параллельности, квалифицированные ролевые исполнители и результаты тестов.

Состояния: `discovery → design → planning → implementation → verification → release → done`. Для задачи без интерфейса `design` может фиксировать применимость как `not-applicable`; для низкого риска допустим `lite` с сокращённым перечнем evidence.

## Обязательная регистрация и проверка задач

До реализации `standard`, `critical` и всех существенных UI-изменений создай задачу через `aek.py new-task`. Для `lite` без интерфейса локальная запись задачи необязательна, но реальный продукт всё равно проверяется по риску. Если агент не вызвал локальный контроллер, тот сам не сможет его остановить: нужен обязательный CI с вызовом `aek.py verify` и правилами защиты ветки.

Для UI браузер или документированное исключение должны быть определены **до согласования дизайна**. Отчёт `browser_capability` регистрируется в задаче; без браузера последующая визуальная приёмка не считается выполненной. При отсутствии разрешения на исключение задача остаётся в `verification`, а результат обозначается «не проверено».

Для HTTP API, доступа к базе, потоков и асинхронного серверного кода указывай `--runtime http` при создании задачи и проводи подходящий запуск работающего сервера. Матрица проверок находится в `docs/METHODOLOGY.md`.

`record --run` выполняет один проверенный исполняемый файл без командной оболочки, сохраняет лог, код выхода, время, исходный SHA и состояние Git. Необходимо проверять актуальность этих данных относительно принимаемого состояния. `record --file` оставлен для требований, разрешений и содержательных отчётов. Для `tests` и `runtime_smoke` произвольный файл не заменяет запуск.

Проверка `visual_qa` требует структурированного отчёта с реальными снимками экрана через `record --file`. Браузерные тесты запускай отдельно и регистрируй как `tests --run`, а не как произвольный успешный `visual_qa --run`. Нельзя считать снимок доказательством всех взаимодействий. Плохой код выхода не превращается в успешный через исключение. Исключение для **отсутствия браузера или визуальной проверки** возможно лишь с отдельным файлом согласования, указанной причиной и явным режимом `--allow-waiver`. В защищённом CI по умолчанию исключения не допускаются.

## Обязательные основания по переходам (standard/critical)
- Перед `design`: подтверждённый Product Brief и инвентаризация среды; для UI дополнительно документированный статус браузера `browser_capability`.
- Перед `planning`: согласование дизайна для UI (включая основные состояния).
- Перед `implementation`: проверка упрощения архитектуры, security screen, **согласованная матрица Harness & Role Assignment (`routes_confirmed`)**, DAG параллельности. В матрице указаны primary/fallback, подтверждения по моделям и effort, разрешённые классы данных и источник согласования.
- Перед `verification`: фактические изменения и локальные проверки.
- Перед `release`: реальные функциональные тесты, независимое QA по риску, security результаты, Visual QA для **всех** UI-задач, в том числе `lite`, и `runtime_smoke` для HTTP-изменений с соответствующим признаком. Если планируется фактическая публикация новой версии, дополнительно проверить номер версии, совместимость, исходный коммит, результаты сборки и приёмки, сведения об изменениях и миграции согласно `docs/VERSIONING.md`.
- Перед `done`: подтверждение завершения этапа, итоговый отчёт. При публикации выпуска приложить подтверждённую ссылку на доставленную версию, Git-тег или GitHub Release по правилам проекта. Если публикации не было, зафиксировать «принято, не выпущено».

Для переходов нужен существующий путь к артефакту, а не только фраза «готово». Локальный контроллер проверяет существование файла и SHA256, но **не удостоверяет личность согласовавшего и не валидирует содержание разрешений**. Для lite при отсутствии ранее согласованной политики согласование внешних провайдеров и передачи данных всё равно обязательно.

## Важная граница доверия
Локальный файл состояния и CLI не могут удостоверить личность согласовавшего человека или предотвратить их обход тем же пользователем/агентом. Для обязательного контроля требуются GitHub branch protection/rulesets, CI с обязательными статусами, CODEOWNERS, полномочия на approve вне агента и защищённая среда, где исполнитель не может переписать проверки. В этом репозитории CI проверяет **набор AEK**, а не код подключённых проектов.

Нельзя считать отсутствие ошибки `aek.py` полноценной проверкой продукта или безопасности. Команда `verify` только проверяет зарегистрированную задачу и доступные ей локальные свидетельства. Агент способен изменить эти файлы, а команда сама не обнаруживает все типы изменений по именам путей. Для проверяемого результата CI должен повторно выполнять реальные тесты на принятом коммите и требовать обязательного успешного статуса до слияния. Исключения в продукте должны проходить отдельное согласование.

Текущий контроллер AEK не подтверждает автоматически совпадение версии, Git-тега и опубликованных артефактов целевого проекта. Требуются независимые проверки проекта; наличие инструкции не означает техническую блокировку.

## Состояния исполнения и продолжение

Помимо этапа задача хранит `status`: `active`, `blocked`, `failed`, `rework`, `cancelled`. Переходы фиксируют причину и историю. В заблокированном состоянии нельзя продвинуть этап или получить успешный `verify`. `resume` является чтением; препятствие снимается явным `transition --state active` после устранения причины. Отменённые и завершённые задачи нельзя изменять командами регистрации свидетельств.

`rework --to` возвращает на предыдущий этап и исключает результаты последующих этапов из текущих свидетельств, сохраняя их в истории. Поэтому исправление после проверки требует повторной проверки, а ранее согласованный неизменившийся объём не согласуется заново. [Примеры](DAILY_WORKFLOW.md).

## Конкурентная работа и восстановление

Задачи используют `schema_version: 2` и возрастающую `revision`. Сохранение проверяет прочитанную ревизию под блокировкой проекта. Устаревшая запись отклоняется, включая попытку вернуть отменённую задачу в работу. Старые задачи без версии читаются как схема 1 и переводятся в схему 2 при первой явной записи. Неизвестные версии отклоняются.

Изменения задачи и события записываются через сохранённое намерение транзакции. При прерывании между записями чтение останавливается; `state-recover` завершает только проверенное намерение с ожидаемыми хешами. Другой писатель также сначала завершает прерванную транзакцию. При конфликте файлы сохраняются для разбора. Механизм рассчитан на сотрудничающие локальные процессы Linux/macOS, не на распределённую файловую систему или недоверенного писателя.

Проверка имеет отдельный идентификатор попытки. Начало сверяет ревизию и состояние задачи, завершение сохраняет результат независимо от привязки к задаче. Если за время выполнения задачу отменили или изменили, результат остаётся в `.agentic-kit/attempts/`, а привязка отвергается. Отмена задачи сама по себе не прерывает уже выполняемую команду. Процесс, убитый до записи результата, оставляет попытку `running`; статус не выдаёт её за успех. Повтор требует решения исполнителя и актуальной задачи.

`events` читает последовательную историю с курсором. CLI связывает задачи, проверки и операции обновления в общий журнал. Для обновлений события начала/завершения дополняют специализированные журналы файловых и пакетных операций, не заменяют их. Незавершённое событие начала требует проверки соответствующего журнала через `doctor` и `recover`; оно не доказывает успех или откат. Прямые вызовы вспомогательных Python API не являются журналируемым интерфейсом обновления.

Локальные записи доступны тому же пользователю, что и проект. Они помогают восстановить работу, но не удостоверяют человека, разрешение или независимую проверку.

[Повторяемые процессы change/fix/update](PROCESSES.md) сохраняют определение, зависимости, попытки и доказательства. Продолжение задачи после смены сессии использует сохранённое состояние, а не предположение по переписке.

## Предел поручения

Условия перехода не разрешают расширять поручение пользователя. Перед продвижением проверяется сохранённая `execution_boundary`; по умолчанию новая задача останавливается после verification. Даже успешные tests, independent_review и release_approved не разрешают пересечь эту границу. Порядок изменения и миграции описан в [PROCESSES.md](PROCESSES.md).
