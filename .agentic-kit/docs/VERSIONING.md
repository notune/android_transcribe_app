# Управление версиями и выпусками

Обязательная часть AEK при подготовке выпуска продукта. Для внутренних опытных проектов, у которых пока нет выпусков, достаточно сохранить изменения и их проверки. Номер версии, Git-тег или GitHub Release не нужны после каждого коммита.

## Различай три события

| Событие | Результат | Связь с выпуском |
|---|---|---|
| Коммит | Сохранённые изменения и их проверки | Сам по себе не является выпуском |
| Принятый этап | Точный SHA, принятые требования, доказательства приёмки | Может остаться частью будущей версии |
| Выпуск | Согласованный номер, принятый код, сведения об изменениях и распространённые артефакты | Реальное опубликованное состояние |

Состояния «принято, не выпущено», «готово к выпуску, ожидает разрешения» и «опубликовано» нельзя смешивать.

## Выбор версии

1. В начале продукта выбери схему версий и главный источник номера. Для библиотек, CLI и продуктов с публичным контрактом по умолчанию подходит SemVer: `MAJOR.MINOR.PATCH`.
2. `PATCH` для совместимых исправлений, `MINOR` для совместимых дополнений, `MAJOR` для несовместимых изменений в стабильном контракте.
3. Для `0.x.y` публичный интерфейс ещё может меняться. Значимое изменение удобно выделять новой `0.MINOR.0`, но номер не заменяет объяснение фактической совместимости.
4. Предварительные версии обозначай, например, `1.2.0-rc.1`. Наличие этого суффикса в исходниках само по себе не доказывает, что выпуск опубликован.
5. Для приложений без публичного API допустима иная понятная схема. Отдельные версии приложения, API, протокола и формата данных меняй независимо, когда у них разный жизненный цикл.
6. Завершение этапа не обязано менять номер версии. Несовместимое изменение нельзя выпускать под прежним номером без явного решения и объяснения.

## Единственный источник и журнал изменений

Выбери главный файл версии: `pyproject.toml`, `package.json`, `VERSION` или соответствующий механизм платформы. Другие значения, например CLI `--version`, метаданные API/MCP, собранный пакет и документация, должны с ним совпадать. Если файл блокировки зависимостей содержит версию собственного пакета, обновляй его штатным способом.

В `CHANGELOG.md` отделяй «В разработке» от уже опубликованных версий. Не дописывай новые возможности в раздел прежнего выпуска. Для несовместимых изменений и миграции данных готовь инструкцию перехода и безопасного отката; для простой совместимой правки отдельная инструкция не нужна.

## Подготовка кандидата

1. Определи принятые изменения и предложи версию. Получи согласование влияния на пользователей и совместимость.
2. Зафиксируй **полный SHA** кандидата. Не считай плавающий `main` доказательством конкретного выпуска.
3. Сверь исходный номер, производные значения, `CHANGELOG.md`, описание контракта и миграции по необходимости.
4. Выполни необходимые тесты, анализ безопасности, независимую приёмку по риску, сборку и пробную установку. Подтверди связь результатов **с выбранным коммитом**. Если код изменился, необходимые проверки повторяются.
5. Для реально собранных артефактов запиши SHA256 по необходимости. Не придумывай контрольные суммы. Для критичных поставок дополнительно проверь зависимости, подписи и происхождение артефактов.
6. Заполни `templates/RELEASE_CHECKLIST.md`. Предъяви нерешённые проблемы, проверенные ограничения и план возврата к предыдущей версии.

Удобно отделить повышение номера версии в отдельный коммит, но это не обязательное правило. Важно совпадение итоговой версии, принятого кода и доказательств, а не число коммитов.

## Git-теги и GitHub Releases

Если Git принят реестром выпусков, используй теги вида `vX.Y.Z` или `vX.Y.Z-rc.N`. Предпочитай аннотированные теги, созданные на **точном принятом коммите**. Перед отправкой проверяй существование тега и соответствие версии. Не передвигай и не переиспользуй опубликованный тег. Для исправления опубликованного продукта готовь новый выпуск.

GitHub Release при принятом порядке создаётся на проверенном теге и содержит описание изменений, сведения о совместимости, миграции и ссылки на артефакты. Отправка тега, создание Release, публикация пакета и развёртывание требуют **отдельного разрешения**. Разрешение создать обычный коммит не даёт прав публиковать новую версию.

Не создавай исторические теги на текущем коммите только потому, что в его файлах указан старый номер. Исторический тег допустим лишь при достаточных доказательствах именно того принятого исходного состояния. Если таких доказательств нет, прямо скажи об отсутствии подтверждённого выпуска.

Применяй защищённые правила репозитория, CI и отдельные права на публикацию там, где это возможно. Инструкции агента сами по себе не являются технической защитой.

## Что проверяет сам AEK

AEK хранит свой текущий номер в `VERSION`, а записи о изменениях в `CHANGELOG.md`. Команда `python3 tools/check_aek_version.py` проверяет формат SemVer и согласованность этих двух файлов, а аргумент `--tag` позволяет сравнить имя Git-тега с версией. Она ничего не публикует и не проверяет готовность чужих продуктов.

Нынешний `aek.py` не проверяет версии и Git-теги всех подключённых проектов: их собственный CI должен учитывать конкретный стек, тесты, контракт и порядок поставки.
