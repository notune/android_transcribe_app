# Процессы change, fix и update

Процесс связывает шаги задачи с зависимостями и проверяемыми результатами. Он хранится в той же задаче, что этапы, доказательства и контекст. Пользователь вызывает существующие `/aek_change`, `/aek_fix`, `/aek_update`; новых slash-команд нет. CLI `process` предназначен для агента и диагностики.

Это декларативные JSON-описания из `workflows/`, без команд оболочки и автономного запуска агентов. Контроллер проверяет этап, зависимости, доказательства и предел попыток. Текстовые `stop_conditions` объясняют исполнителю, когда остановиться; они не являются исполняемыми проверками.

## Создание и продолжение

```bash
python3 .agentic-kit/tools/aek.py new-task --target . --id TASK-001 \
  --title "Добавить экспорт" --profile standard --process change
# Для исправления выбери --process fix, для обновления окружения --process update.
python3 .agentic-kit/tools/aek.py process status --target . --task TASK-001
```

Профиль выбирается по риску; при применимости добавь `--ui` и `--runtime http`. Процесс дополняет обязательные условия профиля из [WORKFLOW.md](WORKFLOW.md), включая браузер и серверные проверки.

Существующую задачу без процесса можно продолжать обычными `record` и `advance`. Присоединить процесс через `process start --name change|fix|update` можно только в `discovery`. Уже пройденные этапы задним числом не подтверждаются. Задачу после `discovery` не пересоздавай только ради процесса; применяй его к следующей новой задаче.

При старте сохраняются полное определение процесса и его SHA256. Обновление кита не заменяет этот снимок: `process status` сообщает `definition_changed`, но продолжает проверять сохранённое определение. Другое определение применяется к новой связанной задаче. Повторный `process start` существующий процесс не заменяет.

## Один этап: start, record, finish, advance

Имена шагов совпадают с этапами: `discovery`, `design`, `planning`, `implementation`, `verification`, `release`. Каждый следующий шаг зависит от предыдущего. Для каждого этапа выполняй эту последовательность:

1. `process start-step --step STAGE`: отметить начало работы. Разрешены только текущий этап активной задачи, актуальные зависимости и входные данные.
2. Выполнить работу; сохранить настоящие документы через `record --file`, проверки через `record --run`.
3. `process finish-step --step STAGE --outcome passed`: подтвердить все требуемые доказательства. Один флаг `passed` без них не принимается.
4. `advance --to NEXT_STAGE`: перейти ровно на следующий этап. Ни `record`, ни `finish-step` этап не меняют.

Пример первого этапа задачи `lite` после фактического согласования объёма:

```bash
python3 .agentic-kit/tools/aek.py process start-step --target . --task TASK-001 --step discovery
python3 .agentic-kit/tools/aek.py record --target . --task TASK-001 \
  --key scope_approved --file docs/evidence/scope.md
python3 .agentic-kit/tools/aek.py process finish-step --target . --task TASK-001 \
  --step discovery --outcome passed
python3 .agentic-kit/tools/aek.py advance --target . --task TASK-001 --to design
```

Для `standard` и `critical` добавь все основания текущего профиля. Даже шаг без применимых доказательств нужно явно начать и закончить. `process status` показывает `ready`, состояние, попытки, недостающие результаты и `stale` для устаревшего подтверждения.

В `verification` сначала начни шаг, выполни проверки на чистом просмотренном коммите, затем заверши шаг и вызови `verify`. После успешного `verify` можно переходить в `release` только если сохранённая граница выполнения разрешает этот этап. Шаг `release` фиксирует передачу результата и необходимые основания для `done`; это не разрешение публиковать или развёртывать продукт.

## Исполнимость плана

На шаге `planning` план считается готовым, если по каждому обязательному шагу другой исполнитель может назвать действие, наблюдаемый результат, команду или способ проверки, разрешённые пути и зависимости. Заглушки `TBD`, `TODO`, «аналогично задаче N», «добавить обработку ошибок» и «написать тесты» не принимаются. Для `lite` достаточно одной строки на шаг. Для `standard` и `critical` проверь покрытие каждого критерия приёмки. Если процесс или профиль требует сохранения плана, используй `record --file`. Для `lite` без локальной задачи отдельный файл не обязателен. SHA сохранённого плана подтверждает версию, но не исполнимость.

## Порядок поставки

План даёт проверяемый результат на текущих требованиях прежде, чем расширение: для новой возможности это минимальный работающий сквозной сценарий, для исправления воспроизведение дефекта и подтверждённая причина, для обновления план и восстановление. Обобщение, необязательное расширение конфигурации и оптимизация идут после проверки этого результата. Пункт, который нельзя проверить до появления будущих требований, в план не входит.

## Дополнительные результаты

| Процесс | Этап | Дополнительные ключи `record --file` |
|---|---|---|
| `change` | Все | Только обычные требования выбранного профиля |
| `fix` | `planning` | `root_cause`: воспроизведение, ожидаемое и фактическое поведение, подтверждённая причина |
| `fix` | `verification` | `regression_check`: проверяемый сценарий и связь с реально выполненными тестами |
| `update` | `discovery` | `environment_inventory`: установленные компоненты, версии, локальные изменения |
| `update` | `planning` | `update_plan`, `recovery_plan`: точный план, конфликты, область влияния и восстановление |
| `update` | `implementation` | `update_result`: результат по каждому компоненту и журнал применения |
| `update` | `verification` | `environment_check`: фактическая проверка окружения после применения |

Эти документы содержат результаты и ссылки на исходные свидетельства. Для обновления сохраняй настоящий `plan_id`, SHA источника, идентификаторы запуска и резервных копий, пути журналов, точные команды восстановления. Документ не превращает частичный сбой в успех. `regression_check` и `environment_check` не заменяют обязательные выполненные `tests` и другие проверки профиля.

План и применение обновления выполняются по [COMPONENTS.md](COMPONENTS.md) и [UPGRADE.md](UPGRADE.md). Процесс не запускает пакетные менеджеры и не повторяет применение автоматически. После обновления кита продолжай задачу по закреплённому определению.

## Блокировки, повтор и доработка

Состояние задачи и состояние шага различаются. Неуспешную попытку фиксируй через `process finish-step --outcome failed --reason TEXT`; внешнее препятствие через `--outcome blocked --reason TEXT`. При остановке всей задачи также используй `transition --state failed|blocked --reason TEXT` и сохрани контекст по [DAILY_WORKFLOW.md](DAILY_WORKFLOW.md).

После устранения причины сначала очисти решённые `context.blockers` и явно верни задачу в `active`, если она была остановлена. Для шага `blocked` используй `process resume-step --step STAGE --reason TEXT`: он продолжится в той же попытке. `resume` сам ничего не разблокирует и не подтверждает согласования.

Для `failed` доступен `process retry --step STAGE --reason TEXT`, затем новый `start-step`. В `change` и `fix` повторяются только `implementation` и `verification`, максимум три попытки каждого шага за цикл. Пройденный шаг повторить нельзя. Остальные шаги и все шаги `update` имеют одну попытку. Исчерпание лимита требует разбора причины и явного решения о доработке.

Если исправление требует возврата на предыдущий этап, используй `transition --state rework --to implementation --reason TEXT` (или более ранний этап по характеру изменения), затем `transition --state active --reason TEXT`. Контроллер архивирует прежние шаги и их доказательства, очищает результаты с точки возврата и начинает новый явный цикл. Не используй доработку как автоматический обход лимита. После сбоя обновления сначала изучи журнал и восстановление, затем подготовь новый точный план; повторный запуск старого применения недопустим.

## Повторные проверки и CI

Повторный `record --run` создаёт новое доказательство даже при той же команде и SHA. Уже пройденный шаг `verification` становится устаревшим. После успешного повторного запуска обнови ссылки на доказательства:

```bash
python3 .agentic-kit/tools/aek.py record --target . --task TASK-001 \
  --key tests --run "python3 -m unittest discover -s tests"
python3 .agentic-kit/tools/aek.py process refresh-step --target . --task TASK-001 \
  --step verification --reason "Повторная проверка текущего коммита"
python3 .agentic-kit/tools/aek.py verify --target . --task TASK-001
```

`refresh-step` применим только к уже `passed` шагу не позднее текущего этапа активной незавершённой задачи. Он заново проверяет доказательства, сохраняет число попыток и архивирует предыдущие ссылки. Заменяться могут только реально выполненные `tests` и `runtime_smoke`. Изменение согласований, дизайна или других документов требует явной доработки. Для первого завершения `verification` используй обычный `finish-step`.

[Шаблон CI](../templates/AEK_VERIFY_CI.yml) после повторных тестов вызывает `refresh-step` только если задача имеет процесс и его `verification` уже `passed`. Он не завершает незавершённый шаг автоматически. Для UI/HTTP добавь соответствующие проверки до обновления доказательств. CI по умолчанию не принимает исключения.

Если для `browser_capability` или `visual_qa` уже записано допустимое человеческое согласование исключения, его учёт требует явного `--allow-waiver` в каждом соответствующем `process`, `status`, `resume`, `advance` и `verify`. Сам флаг исключение не создаёт и не разрешает его для других ключей. Без флага статус покажет неудовлетворённое условие; само согласование остаётся в задаче.

## Граница выполнения поручения

Новая задача по умолчанию получает `execution_boundary.stop_after: verification`.
Это предел работы, а не свидетельство пользовательского согласования. Если пользователь
указал другой конечный этап, передай `--stop-after STAGE` при создании задачи.
Для явно указанной границы, отличной от verification, обязательны `--user-message-ref` и `--user-instruction`:
ссылка на настоящее сообщение и его точная формулировка. Не подменяй их собственным отчётом.

Граница включительна: при `verification` можно начать и закончить этот шаг, повторить
проверки, обновить доказательства, выполнить `verify` и сохранить передачу контекста.
Переход в `release` и выполнение его шагов запрещены. Успешный verify не расширяет
поручение; файл `release_approved` также не меняет границу. Оставь задачу на согласованном
этапе и сообщи результат. Не переводи её в done ради красивого статуса.

Явное изменение границы или миграция старой открытой задачи:

```bash
python3 .agentic-kit/tools/aek.py boundary --target . --task TASK-001 \
  --stop-after verification --user-message-ref 'ссылка-на-сообщение' \
  --user-instruction 'Заверши verification и выполни verify.'
```

Используй уже выданное действующее поручение; повторное согласование того же объёма
не требуется. Расширение объёма требует нового разрешения. Команда сохраняет историю
изменения и источник, но локальный CLI не может удостоверить, что текст действительно
написан человеком. Самостоятельная запись агентом `user_message` не создаёт разрешения.

У старых открытых задач без границы продолжение блокируется до явного её указания.
Если старая открытая задача уже находится дальше действительного поручения, сначала
запиши более строгую границу. Статус покажет превышение; работа останется заблокированной.
Затем явно верни задачу через `transition --state rework --to STAGE --reason TEXT`
на допустимый ранний этап. Прежние результаты сохраняются в истории, а последующие
доказательства становятся неактуальными. Не расширяй поручение только ради миграции.

Обновление кита не выбирает предел за пользователя. Исторические done/cancelled
не переписываются. Правила относятся ко всем профилям и к процессу без рецепта тоже.
