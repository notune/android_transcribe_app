# Специализации и ответственность

Восьми специализациям соответствует **функция**, а не требование запускать восемь отдельных экземпляров модели.

| Роль | Зона решения | Обязательный результат |
|---|---|---|
| PM | Ценность, приоритеты, границы MVP, пользовательский диалог | Product Brief, подтверждения |
| BA | Сценарии, ограничения, поведение, критерии приёмки | OpenSpec delta, acceptance |
| Product Designer | UX, UI, адаптивность, состояния и доступность | Дизайн/прототип, visual criteria |
| Architect | Стек, контракты, библиотеки, простота | Architecture Simplification Decision |
| Engineer | Код, интеграции, тесты | Работающий проверенный срез |
| QA | Отрицательные сценарии, интеграция, регрессии | Evidence, дефекты, тестовые результаты |
| Security | Угрозы, данные, полномочия, зависимости | Security screen и findings |
| DevOps/SRE | CI/CD, выпуск, наблюдаемость, rollback | Release evidence |
| Orchestrator | DAG, назначения, лимиты, интеграция, состояние | План и контроль качества |

При старте проекта Orchestrator совместно с PM и Architect применяет `harness-discovery-assignment`: получает факты о доступной среде, уточняет только существенные ограничения, предлагает назначения, согласует с пользователем. Security контролирует передачу данных. Каждая роль исполняется только на согласованном primary/fallback.

PM/BA и Designer могут работать параллельно по согласованным вводным; Architect и Security — совместно. Независимость QA/Security требуется по риску. Одна модель может исполнять несколько ролей при явной смене инструкций и объективных доказательствах.
