# Методология

**Управление:** Product Discovery + Kanban. **Требования и изменения:** OpenSpec. **Инженерное качество:** практики Superpowers, выборочно и по характеру работы. **Безопасность:** Secure SDLC. **Интерфейсы:** Design Before Code.

## Этапы
1. **Harness Discovery & Assignment:** диагностика инструментов и политик доступа; короткий диалог об ограничениях пользователя; проверка моделей, доступных усилий и инструментов; матрица назначения primary/fallback для восьми ролей и Orchestrator. Результат: capability registry и согласованная конфигурация.
2. **Product Discovery:** PM/BA обсуждают с пользователем задачу, пользователей, ограничения, альтернативы и критерии успеха. Результат: согласованный Product Brief.
3. **Specification:** OpenSpec proposal, delta specs, критерии приёмки. В brownfield сохраняется текущее поведение вне согласованного изменения.
4. **Product Design:** UX потоки, экраны и состояния (loading/error/empty), адаптивность, доступность, дизайн-система и согласованный прототип для UI.
5. **Architecture & Security:** решение с минимальной сложностью, библиотечные альтернативы, анализ угроз, доступов, данных и эксплуатационных ограничений. Существенный выбор фиксируй по шаблону [ARCHITECTURE_DECISION.md](../templates/ARCHITECTURE_DECISION.md).
6. **Swarm Planning:** DAG независимых задач с владельцами, границами изменения, отдельными тестовыми ресурсами.
7. **Implementation:** вертикальные срезы, тесты, проверка корневых причин, проверенные скиллы, отдельные worktrees при параллельной записи.
8. **Verification:** обязательный выбор проверок по типу изменения, запуск соответствующего кода и приложения, отдельная проверка браузера для UI, проверка совместимости, безопасности и повторные тесты после слияния. Результаты должны соответствовать точному состоянию Git.
9. **Release & Learn:** различай принятый этап и опубликованный выпуск. Для выпуска согласуй версию, совместимость, точный коммит, реальные результаты приёмки и сборки, сведения об изменениях и миграции по необходимости. Публикация только по разрешению; мониторинг и обратная связь. См. `docs/VERSIONING.md`.

Этапы перекрываются там, где позволяют зависимости; это не девять последовательных встреч.

## Матрица проверок по границе изменения

| Изменение | Минимум проверок, когда применимо |
|---|---|
| Логика, расчёты | Модульные и граничные тесты, пустые данные, ошибки |
| HTTP API | Запуск реального приложения, ожидаемые HTTP-ответы, ошибки и повторные запросы |
| База данных, потоки и асинхронность | Тест жизненного цикла соединений и параллельных запросов на реальной границе сервера |
| Структура базы | Миграция на безопасной копии, повторное применение, обратимость и сохранность данных |
| Веб-интерфейс | Проверка в браузере, пользовательский сценарий, скриншот, консоль, сеть, клавиатура и фокус |
| Доступы | Отрицательные сценарии, `401/403`, разграничение данных и невозможность обойти серверные проверки |
| Внешние системы | Таймауты, неверные ответы, частичные отказы, повторные вызовы и безопасное восстановление |

Для UI изменения в видимом поведении отражай в OpenSpec delta spec, включая новый раздел или вкладку. Для небольшой правки `lite` достаточно компактного `ADDED` или `MODIFIED Requirement` с проверяемым сценарием, если используемый OpenSpec требует такой формат. Не придумывай требования задним числом и не создавай вторую систему спецификаций.

Для HTTP/БД/потоков указывай `--runtime http` в задаче и проверяй рабочее приложение, а не только изолированные функции. При упавшей или не выполненной проверке фиксируй блокирующий статус, пока пользователь явно не изменит план или условия приёмки.

## Профили
- **lite:** низкий риск, локальная небольшая правка, минимум документов; не отменяет базовую безопасность и доказательства.
- **standard:** обычный продукт, Product Brief, OpenSpec, дизайн при UI, архитектурное упрощение, QA, план параллельности.
- **critical:** чувствительные данные, публичная критичная поверхность, финансовые операции или автономные инструменты: независимые security/QA проверки, более строгие approvals, релизный план.

## Критерии готовности
Реализованные требования; фактические результаты тестов; визуальная проверка для UI; security по риску; подтверждённая совместимость; актуальные документы; явные непроверенные пункты. Отчёт агента не заменяет запуск тестов.


## Необязательный Knowledge Management

Для проектов со значительной историей и документацией можно активировать пакет навыков `knowledge-base` на основе OntoShip GitMark. Он обеспечивает поиск и актуализацию знаний между сессиями, но **не** вводит второй `dev-flow`, не меняет OpenSpec и не становится обязательным этапом для небольших задач. Дополнительные проверки выполняются только при активированном пакете и по риску.


## Необязательный Codebase Audit

Для существующих проектов можно активировать `codebase-audit`: проверяемое обследование кода, самостоятельные задания и контроль их актуальности. По результатам анализа пользователь выбирает изменения, которые оформляются через OpenSpec. Назначение исполнителей и выпуск остаются в AEK; пакет навыков не запускает отдельный цикл разработки.
