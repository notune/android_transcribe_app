# Повседневная работа с AEK

Команды запускают процедуры существующего контроллера `tools/aek.py`. В проекте путь к нему: `.agentic-kit/tools/aek.py`. Они не создают второй процесс управления задачами.

## Команды

| Запрос | Результат |
|---|---|
| `/aek_greenfield` | Применение к новому проекту |
| `/aek_brownfield` | Применение к существующему проекту |
| `/aek_update` | План и обновление зарегистрированных компонентов |
| `/aek_change Добавить экспорт` | Изменение с требованиями, выбором риска и проверкой |
| `/aek_fix Не сохраняется форма` | Воспроизведение, причина, исправление, регрессионная проверка |
| `/aek_status` | Текущие задачи, этап, состояние, препятствия |
| `/aek_verify TASK-001` | Запуск согласованных проверок и контроль актуальности результатов |
| `/aek_resume TASK-001` | Восстановление контекста без автоматического снятия блокировок |
| `/aek_audit` | Обследование с проверяемыми замечаниями без автоматического рефакторинга |
| `/aek_doctor` | Установка, реестр, конфликты и непроверенные возможности |
| `/aek_rollback` | Предварительный план отката обновления |
| `/aek_help` | Справка и синтаксис выбранного провайдера |

В Codex используй `$aek-change`, `$aek-fix` и другие навыки с дефисом. Это соответствие формату Agent Skills, а не сохранение старых команд. Подробнее: [SHORTCUTS.md](SHORTCUTS.md).

## Одно состояние задачи

1. Прочитай инструкции проекта и существующую задачу. Не повторяй уже отвеченные вопросы.
2. Для нового изменения определи цель и проверяемый результат. Существенные неизвестные уточни; мелкие детали решай самостоятельно.
3. Выбери `lite`, `standard` или `critical` по риску. Любое UI-изменение отмечай `--ui`, серверное HTTP-изменение `--runtime http`.
4. Создай задачу через `new-task --process change` (исправление: `--process fix`, обновление окружения: `--process update`). Существующую задачу продолжай с её текущим процессом; без процесса после `discovery` используй обычный workflow. Используй существующие требования OpenSpec, не копируй их в отдельную систему.
5. Для каждого шага процесса соблюдай `process start-step → record → process finish-step → advance`; подробности и дополнительные доказательства в [PROCESSES.md](PROCESSES.md). Выполняй применимые контрольные точки и реализуй изменение. Для исправления сначала воспроизведи сбой.
6. Выполни реальные проверки через `record --run`. `verify` проверяет записи, но сам не выбирает и не запускает продуктовые тесты.
7. Сообщи изменения, проверки, ограничения и следующий шаг. Выпуск и развёртывание требуют отдельного поручения.

Авторизация имеет область действия. Одобрение конкретного плана не означает разрешение на новые провайдеры, передачу данных или изменение общих инструментов. Уже полученное согласие в той же области повторно не запрашивай.

## Прерывание и доработка

Этап разработки и состояние исполнения хранятся раздельно. Этапы прежние: `discovery → design → planning → implementation → verification → release → done`. Состояния: `active`, `blocked`, `failed`, `rework`, `cancelled`.

```bash
python3 .agentic-kit/tools/aek.py list-tasks --target .
python3 .agentic-kit/tools/aek.py transition --target . --task TASK-001 --state blocked --reason "Нет тестового сервера"
python3 .agentic-kit/tools/aek.py resume --target . --task TASK-001
# После устранения причины:
python3 .agentic-kit/tools/aek.py transition --target . --task TASK-001 --state active --reason "Тестовый сервер доступен"
# Когда проверка выявила дефект:
python3 .agentic-kit/tools/aek.py transition --target . --task TASK-001 --state rework --to implementation --reason "Сбой сохранения"
python3 .agentic-kit/tools/aek.py transition --target . --task TASK-001 --state active --reason "Начинаю исправление в согласованной области"
```

`resume` ничего не меняет. Он показывает задачу, Git-состояние, недостающие свидетельства и действие для продолжения. Для процесса прочитай также состояния шагов и закреплённое определение. После устранения причины `blocked` шаг продолжается через `process resume-step`; `failed` повторяется через `process retry` только в пределах разрешённого лимита, затем `start-step`. `rework` возвращает на выбранный предыдущий этап и переносит утратившие применимость результаты в историю. Согласования более ранних неизменённых этапов сохраняются. Для нового объёма требований вернись в `discovery`. Отменённая или завершённая задача не открывается повторно, создаётся новая связанная задача.

## Проверка в T3 Code

После установки команд перезапусти агентную сессию и вызови справку у конкретного провайдера. Проверь безопасный просмотр плана и статус. Успешная запись Markdown-файлов не доказывает загрузку команды интерфейсом. Автоматические тесты адаптеров и реальная проверка в T3 Code фиксируются отдельно.

## Переходы этапов и проверяемое состояние кода

`record` сохраняет свидетельство, а этап меняет только `advance`. Перед переходом смотри `status` и обязательные ключи в [WORKFLOW.md](WORKFLOW.md). Например, для задачи `lite` с процессом после фактического согласования объёма:

```bash
python3 .agentic-kit/tools/aek.py process start-step --target . --task TASK-001 --step discovery
python3 .agentic-kit/tools/aek.py record --target . --task TASK-001 --key scope_approved --file docs/evidence/scope.md
python3 .agentic-kit/tools/aek.py process finish-step --target . --task TASK-001 --step discovery --outcome passed
python3 .agentic-kit/tools/aek.py advance --target . --task TASK-001 --to design
python3 .agentic-kit/tools/aek.py status --target . --task TASK-001
```

Дальнейшие переходы выполняются по одному, с применимыми основаниями. UI требует браузера и согласованного дизайна даже в `lite`; для `standard` обязательны основания архитектуры, безопасности и назначения исполнителей. Перед итоговой проверкой задача должна достигнуть `verification`.

Принимаемые результаты `record --run` относятся к чистому текущему Git-коммиту. Согласуй и зафиксируй проверяемое изменение до финального запуска; не включай пользовательские посторонние изменения в коммит. Для диагностики до коммита допустим `--allow-dirty --reason TEXT`, но такой запуск не засчитывается при приёмке. После нового изменения повторяются проверки, результаты старого коммита недействительны.

## Контекст между сессиями

Сохраняй в задаче владельца, ветку, рабочую директорию, согласованную область, краткий итог, следующий конкретный шаг и препятствия. `status` и `resume` показывают эти данные вместе с Git-состоянием, последней попыткой и состоянием процесса. Это запись для передачи работы, а не блокировка Git-ветки или автоматическое назначение исполнителя.

Для передачи задачи другому агенту или новой сессии используй [AGENT_HANDOFF.md](../templates/AGENT_HANDOFF.md): сначала полный текст поручения, критерии приёмки и границы записи, затем возврат результата со ссылками на evidence.

Подготовь JSON-файл с изменяемыми полями, например `docs/evidence/task-context.json`:

```json
{
  "owner": "исполнитель задачи",
  "branch": "feature/TASK-001",
  "worktree": "/absolute/path/to/project",
  "scope": "Экспорт текущей выборки",
  "summary": "Реализация готова, требуется проверка",
  "next_action": "Выполнить согласованный регрессионный тест",
  "blockers": []
}
```

```bash
python3 .agentic-kit/tools/aek.py context --target . --task TASK-001 --file docs/evidence/task-context.json
python3 .agentic-kit/tools/aek.py resume --target . --task TASK-001
python3 .agentic-kit/tools/aek.py events --target . --task TASK-001
```

Укажи фактические значения; при необходимости добавь `base_commit`. Передаваемые поля объединяются с сохранённым контекстом. `blockers` заменяется целиком; очисти его через `[]` только после устранения причин. Непустые препятствия запрещают продолжать шаги процесса, переходить этап и принимать результат. Переход в `active` сам их не удаляет.

Обновление задачи проверяет её ревизию, поэтому параллельный устаревший результат не затирает более новую запись. При конфликте перечитай `status` и последние `events`, сопоставь изменения и продолжи с актуальным состоянием. Не редактируй JSON задачи вручную. После прерванной записи используй диагностическое восстановление из [CLI.md](CLI.md).

При повторном запуске тестов уже пройденного `verification` обнови его доказательства через `process refresh-step`, затем повтори `verify`. Это не расходует попытку и не подтверждает документы заново. Условия, исключения и пример CI описаны в [PROCESSES.md](PROCESSES.md).

Перед продолжением восстанови границу поручения `execution_boundary`. По умолчанию новая задача заканчивает работу на verification. Переход к release/done допускается только в пределах явно разрешённого объёма; собственный файл одобрения не расширяет его. Старую открытую задачу без границы мигрируй явно по [PROCESSES.md](PROCESSES.md).
