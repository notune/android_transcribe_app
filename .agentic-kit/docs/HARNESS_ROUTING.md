# Harness Discovery & Assignment

## Назначение

Перед существенной разработкой **нового или существующего проекта** выяви фактически доступные агентные харнессы, проверь возможности, выясни ограничения пользователя, затем предложи и согласуй матрицу назначения ролей. Повторяй только при существенных изменениях доступности, требований или политики данных.

**Подключение харнесса не равно возможности его запустить.** AEK описывает выбор и проверки; фактическое делегирование требует поддерживаемого инструмента в среде ведущего агента.

## 1. Environment Discovery (без изменения среды)

Обследуй Codex, OpenCode, DSH, Qwen Code, Pi и другие обнаруженные инструменты.

- Узнай исполняемую команду, путь, версию, доступные инструменты, skills/MCP и изоляцию.
- Модели, reasoning effort, авторизацию и ограничения проверь отдельно; наличие CLI само по себе **не подтверждает их**.
- Для каждой связки `harнесс + модель` укажи статус: `discovered`, `user_reported_tested`, `verified_in_environment` или `unavailable`.
- Фиксируй дату, происхождение подтверждения, разрешённый класс данных, возможности браузера/изображений, лимиты и стоимость.
- Не сканируй секреты и токены. Не запускай сетевые запросы или тесты с передачей исходного кода без разрешения.

Начальная безопасная проверка: `python3 tools/aek.py inspect --target /path/to/project`. Она обнаруживает только кандидатов, а не подтверждает работоспособность моделей.

## 2. Минимальный диалог с пользователем

Сначала самостоятельно изучи окружение, потом выясни **только неизвестные** существенные ограничения:

1. Разрешено ли применять обнаруженные харнессы и передавать код/данные соответствующим провайдерам?
2. Есть ли ограничения бюджета, стоимости, квот, максимального параллелизма и доступа к инфраструктуре?
3. Есть ли предпочтения или запреты по моделям, а также разрешённые резервные модели?

Не задавай эти вопросы повторно, если ответы уже известны, актуальны и покрывают текущий проект. Не превращай диалог в длинную анкету. Если неизвестная граница доступа мешает безопасному выбору, задай один конкретный вопрос.

## 3. Capability Assessment

При разрешении пользователя выполни небольшие контрольные задания. Для каждой роли сравни качество **по проверенным задачам**, инструментальные возможности, безопасность, задержки, стоимость и лимиты. Уровни рассуждения указывай точными идентификаторами только после фактической проверки данной связки. Иначе запиши `unknown`.

Для моделей с пометкой Uncensored нельзя автоматически предполагать ни отсутствие безопасности, ни достаточность защиты. Применяй те же проверки и ограничения передачи данных, с дополнительным вниманием к доступу к инструментам.

Не назначай максимальную модель всем ролям по умолчанию. Не придумывай доступные режимы и возможности.

## 4. Role Assignment Proposal

Подготовь таблицу на 8 специализаций + функцию Orchestrator:

- основной харнесс, точная модель, уровень рассуждения, если подтверждён;
- необходимые инструменты и скиллы;
- допустимые операции, классы данных и предел параллелизма;
- резервная связка с теми же ограничениями;
- обоснование назначения и статус проверки.

Шаблон: `templates/HARNESS_ASSIGNMENT.md`. Одна модель может исполнять несколько ролей. Используй только фактически подходящие и разрешённые маршруты; неизвестное обозначай `TBD`.

## 5. Approval & Persistence

Покажи пользователю единую рекомендуемую конфигурацию; предложи утвердить её целиком или изменить отдельные назначения. Согласуй поставщиков, передачу кода/данных, существенные полномочия и бюджет.

Зафиксируй capability registry, матрицу и ссылку на реальное согласование. Для standard/critical **до implementation** обязательное evidence `routes_confirmed` должно ссылаться на утверждённую матрицу. Для lite-профиля используй действующее согласованное назначение или получи подтверждение перед работой с новым провайдером.

Локальный SHA256 доказательства не удостоверяет личность пользователя; для доверенного исполнения нужны внешние approvals и защищённые проверки.

## 6. Execution / Review

Orchestrator распределяет задачи между утверждёнными связками и согласованными резервами. Без доступного исполнительного инструмента он **не может** автоматически запустить внешний харнесс. При недоступности primary допускается только заранее утверждённый fallback; новые провайдеры, передачу данных, существенные полномочия и расходы нужно согласовать повторно.

Периодически пересматривай назначения по фактическим результатам; не выполняй полную диагностику на каждом небольшом исправлении.

Примеры и шаблоны:
- `templates/HARNESS_DISCOVERY.md`
- `templates/HARNESS_ASSIGNMENT.md`
- `examples/five-harnesses.user-inventory.json`
- `examples/capability-registry.example.json`
