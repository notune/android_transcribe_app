# Новый проект: каталог, кит, навыки, поток

Применяй, когда пользователь просит создать новый проект, а не изменить существующий.
Результат одной операции: пустой каталог превращается в готовый проект с комплектом AEK,
командами выбранного провайдера, каркасом документации и первым коммитом; проект
регистрируется в интерфейсе, и в нём открывается поток для дальнейшей работы.

Порядок ниже не является разрешением на произвольные действия: сеть, установка и запись
выполняются в границах поручения пользователя. Глобальные настройки T3, права доступа,
чужие проекты и секреты не затрагиваются.

## 1. Что создать

| Раздел | Содержимое | Кто создаёт |
|---|---|---|
| `.agentic-kit/` | кит, инструменты, документы, шаблоны, рабочие процессы | `new-project` |
| `.agents/skills/` | активированные навыки AEK | `new-project` |
| `.opencode/commands/` (или каталог провайдера) | короткие команды `/aek_*` | `new-project` |
| `AGENTS.md` | точка входа в инструкции; правила проекта дописываются отдельно | `new-project`, затем агент |
| `README.md` | название и базовые команды проверки | `new-project` |
| `.gitignore` | окружение, токены, артефакты сборки | `new-project` |
| `docs/` | индекс документации, `docs/evidence/`, бриф на стадии discovery | `new-project` |
| `reports/` | отчёты операций и необработанные ответы инструментов | `new-project` |
| `.agentic-kit/environment.lock.json`, `.aek/` | снимок окружения и манифест команд | `new-project` |
| Git-репозиторий | первый коммит «каркас проекта и подключение AEK» | `new-project` |
| Запись в интерфейсе | проект с тем же `workspaceRoot` | агент через инструменты T3 |
| Поток | full-access поток в новом проекте с brief на discovery | агент через инструменты T3 |

Код приложения, зависимости, CI и OpenSpec в каркас не входят: они появляются по брифу
и задаче, а не автоматически.

## 2. Источник кита

1. Возьми чистый клон `https://github.com/kelvmg/agentic-engineering-kit` **вне** целевого
   проекта. Разрабатываемая ветка и изменённый рабочий каталог проверенным источником
   не являются.
2. Зафиксируй полный commit SHA и `VERSION`. Для нового проекта бери свежий `origin/main`;
   если он новее последнего одобренного SHA, отметь это в отчёте.
3. Убедись, что дерево источника чистое. `source_dirty: true` в результате означает, что
   установлен непроверенный источник, и это нельзя выдавать за проверенную установку.

## 3. Единый план и применение

Целевой каталог должен существовать и быть пустым (допускаются `.git`, `.gitignore`,
`README`, лицензия и начальные инструкции). Значимый код требует режима `existing`
и команды `install`, а не `new-project`.

```bash
# План: ничего не пишет
python3 tools/aek.py new-project --target /absolute/path/to/project \
  --title "Название проекта" --provider opencode

# После просмотра плана: те же аргументы и точный plan_id
python3 tools/aek.py new-project --target /absolute/path/to/project \
  --title "Название проекта" --provider opencode \
  --apply --plan-id PLAN_ID
```

`--provider` повторяемый: `claude`, `codex`, `opencode`, `pi`. Без него навыки
активируются, но короткие команды провайдера не устанавливаются.

План показывает версию кита, `plan_id`, конфликты, состав каркаса и вложенный план
установки. Применение отклоняется при устаревшем `plan_id`, конфликте файлов или
непустом каталоге; частичная запись не остаётся.

Применение выполняет по порядку: установку кита с активацией навыков, каркас, команды
провайдера, снимок окружения, `doctor`, `git init` и первый коммит. Результат содержит
`checks` (`install`, `shortcuts`, `environment`, `doctor`, `git`), идентификаторы планов
и `handoff` для интерфейса. `git` входит в `checks`: сбой инициализации или первого
коммита делает `passed: false` и код возврата 2, а не только запись в `warnings`.

Git-граница важнее удобства:

- План заранее показывает `git.action`: `init` — собственного репозитория нет,
  `init_nested` — каталог лежит внутри чужого репозитория, `commit` / `keep_history` —
  свой репозиторий без коммитов или с историей.
- Если каталог находится внутри другого репозитория, создаётся отдельный репозиторий
  в самом проекте. Родительская история, индекс и незакоммиченные файлы не затрагиваются;
  `git.nested_in` называет родительский корень. Операция сообщает об этом в `warnings`.
- Коммит собирается только из путей каркаса и установленного кита, без `git add -A`:
  чужие и посторонние файлы в коммит не попадают. Список — в `git.staged`.
- Принимается только обычный репозиторий, созданный `git init`: без симлинков внутри
  `.git`, без gitfile, `commondir`, `config.worktree`, `modules`, `worktrees`,
  `objects/info/alternates` и grafts, без внешнего `core.worktree` (с учётом
  `include.path`/`includeIf`). Любое отклонение даёт `git.action: refuse` до записи,
  а не попытку угадать безопасный путь. Непустой индекс без истории
  (`git.index_entries`) тоже блокирует запуск, иначе первый коммит включил бы чужие
  записи индекса. Частичный клон отклоняется: `extensions.partialClone`,
  `remote.*.promisor`, `remote.*.partialclonefilter`, `core.alternateRefsCommand` и
  маркеры `*.promisor` в `.git/objects/pack` дают `refuse`, потому что `git fsck` не
  доказывает наличие объектов, которые Git не хранит локально. Структурные проверки
  (хранилище, включаемые файлы, конфигурация) выполняются до первого обращения Git к
  ссылкам и объектам и до полного `git fsck`, поэтому отказ по частичному клону не
  зависит от того, как fsck трактует обещанные объекты. Иначе обычный `git show-ref`
  при известном promisor-источнике сам подгрузил бы отсутствующие объекты и изменил
  `.git` во время построения плана, который обещает не писать.
- Неполный или повреждённый `.git` не считается отсутствующим: если каталог `.git`
  есть, но в нём нет обязательных `HEAD`, `objects` и `refs` или `git rev-parse
  --show-toplevel` не подтверждает его как репозиторий этого каталога, `git init` поверх
  него не выполняется и план возвращает отказ. Минимальный набор проверяется по файловой
  системе до чтения конфигурации, поэтому пустой `.git` не даёт ошибку Git о конфиге. История,
  у которой `HEAD` ссылается на отсутствующий или не-коммитный объект, тоже отклоняется:
  кит не переписывает повреждённую историю и не объявляет её сохранённой.
- Локально полная история обязательна: непустая граница `.git/shallow` означает
  усечённый клон, где родительские объекты отсутствуют по замыслу, а `git fsck --full`
  считает такую историю нормальной. Shallow-клоны отклоняются так же, как частичные.
- Жёсткие ссылки внутри `.git` отклоняются (кроме `objects/` и `hooks/`): журнал
  Git дописывается через общий inode, поэтому жёсткая ссылка из `.git/logs`, `refs`,
  индекса или конфигурации на файл вне цели означала бы запись в чужой файл при
  коммите. Объекты и pack-файлы разрешены: они неизменяемы и ими законно делятся
  локальные клоны.
- Целостность достижимых объектов проверяется полным `git fsck --full`: отсутствующий
  tree/blob и объект с несовпадающей контрольной суммой дают `refuse`, а не `passed: true`.
  Полная проверка может быть дорогой на крупном репозитории; её таймаут тоже даёт
  `refuse`, а не успех.
  Проверка повторяется при применении, поэтому удаление объекта между планом и
  применением не проходит как успех, даже если `plan_id` не изменился.
- Вложенность определяется обходом файловой системы, без вопроса Git: план не читает
  конфигурацию и includes родительского репозитория, поэтому FIFO или нечитаемый include
  там не могут повесить создание проекта. Собственный `.git` цели всегда проверяется
  полностью.
- Нечитаемые ссылки и индекс блокируют план до записи. Ошибка `git show-ref`,
  повреждённый `packed-refs`, битая ветка (включая текущую) и неразрешимый detached
  `HEAD` дают `refuse`; ошибка `git ls-files --cached` тоже отказ, а не пустой индекс.
  Только действительно новая ветка без коммитов считается отсутствием истории.
  Проверки хранилища, конфигурации и читаемости индекса выполняются и при
  `keep_history`: репозиторий с историей и повреждённым индексом или внешним
  хранилищем отклоняется, хотя записи в него не было бы.
- Симлинки и нерегулярные файлы (FIFO, сокеты, устройства) внутри `.git` и `refs`
  отклоняются: Git не должен читать через них и не должен на них зависать. Глубокая
  проверка хранилища выполняется до первого обращения Git к объектам и ссылкам,
  поэтому FIFO в `objects` или `refs` даёт отказ, а не зависание плана.
- Включаемые файлы конфигурации проверяются до `git config --includes`: каждый
  существующий `include.path`/`includeIf.*.path` должен вести на обычный файл внутри
  цели. Симлинк, FIFO или путь за пределы цели дают `refuse`, иначе Git открыл бы чужой
  файл или завис на специальном. Отсутствующий include разрешён: Git его игнорирует.
  Относительный `core.worktree` разрешается от каталога `.git`, как это делает Git.
- Незавершённая операция Git блокирует запуск: `MERGE_HEAD`, `CHERRY_PICK_HEAD`,
  `REVERT_HEAD`, `REBASE_HEAD`, `BISECT_*`, `sequencer`, `rebase-merge`,
  `rebase-apply` и lock-файлы (`index.lock`, `HEAD.lock`, `shallow.lock`,
  `refs/heads/*.lock` и другие) дают `refuse` до установки, а не частичную запись с
  падением коммита. Проверка маркеров выполняется до решения о `keep_history`, поэтому
  незавершённый merge не считается сохранённой историей.
- Состояние Git входит в `plan_id` как `state_digest`: содержимое `HEAD`, все ссылки
  и символические ссылки, содержимое `packed-refs` и `shallow`, маркеры незавершённых
  операций. Если между планом и применением появилась история, сменилась ветка,
  символическая ссылка или содержимое `packed-refs`, изменилось действие
  (`init` → `keep_history`), состояние хранилища или индекс, старый `plan_id`
  отклоняется как устаревший.
- План и применение проверяют состояние заново: `ensure_git_repository` повторно строит
  план, целостность объектов и читаемость индекса перед записью. Остаётся узкое окно для
  локального процесса, который меняет `.git` между проверкой и `git add`/`commit`; оно не
  расширяет права на запись и закрывается только внешней изоляцией.
- Если у собственного репозитория уже есть история, новый коммит не создаётся
  (`keep_history`), а созданные файлы остаются незакоммиченными для решения пользователя.
  Переписывать чужую историю, делать `reset`, `clean` или `stash` кит не будет.
- Bootstrap запускает Git с очищенным окружением: переменные `GIT_*` и `GIT_CONFIG_*`
  отбрасываются, глобальная и системная конфигурация не читаются, hooks, `core.fsmonitor`
  и GPG-подпись отключены. Личные `user.name`, `user.email` и `init.defaultBranch`
  передаются явно (`-c`) после чтения без исполнения.
- Локальная конфигурация проверяется вместе с `include.path` и `includeIf`; драйверы
  `filter.*.clean/smudge/process` отклоняются. Если хранилище или конфигурация не
  читаются либо превышают лимит проверки, bootstrap отказывается, а не угадывает.

## 4. Регистрация проекта и новый поток

`new-project` не вызывает T3: кит остаётся переносимым между провайдерами. В T3 Code
зарегистрируй проект и открой поток по `handoff` из результата:

| Шаг | Инструмент | Аргументы |
|---|---|---|
| Регистрация | `t3_project_create` | `title`, `workspaceRoot` = абсолютный путь проекта |
| Проверка | `t3_project_list` | проект присутствует, `workspaceRoot` совпадает |
| Поток | `t3_thread_launch` | `projectId` из регистрации, `runtimeMode: full-access`, `title`, `message` |

Правила:

1. Регистрируй каталог один раз. Уже зарегистрированный каталог инструмент отклоняет:
   тогда используй существующий `projectId`, а не создавай дубль.
2. Идентификатор, который вернул T3, записывай ровно в том виде, в каком он принимается
   инструментами. Некоторые развёртывания добавляют префикс (`mcp:`), и «голый» UUID
   тем же инструментом не находится. Проект с таким id открывай через
   `t3_thread_launch`: `create_threads` не открывает поток в таком проекте, а молча
   создаёт его в текущем каталоге, то есть в чужом проекте.
3. Поток открывай после успешных `checks`. Если проверки не passed, сначала разберись
   с причиной: поток в сломанном проекте создаёт ложное впечатление готовности.
4. Запись в локальный реестр установок регистрацию в интерфейсе не заменяет.
5. Если инструменты T3 недоступны, передай `handoff` сессии, которая умеет регистрировать
   проекты, и явно скажи, что регистрация не выполнена.

## 5. Что проверить после применения

```bash
python3 .agentic-kit/tools/aek.py doctor --target /absolute/path/to/project
python3 .agentic-kit/tools/aek.py environment check --target /absolute/path/to/project
git -C /absolute/path/to/project log --oneline -1
```

Ожидается: `doctor` passed с `next_action: verify_provider_visibility`, окружение
`passed: true` и `matches: true`, один коммит каркаса, чистое дерево.

Видимость навыков у провайдера остаётся `unverified`: наличие файлов не доказывает,
что сессия загрузила инструкции. Подтверждение — реальный прогон палитры команд в новом
потоке; результат фиксируется отдельно по каждому провайдеру.

### Одноразовые проверочные проекты

Живой прогон `new-project` выполняй на заведомо одноразовом каталоге и удаляй его после
записи свидетельств: проверочный проект не остаётся на диске и не попадает в реестр
установок. Порядок:

1. Запиши отчёт и свидетельства (вывод `checks`, коммит, `doctor`, ответы потока) в
   постоянный репозиторий вне удаляемой цели — например, в управляющий проект. Отчёт,
   лежащий только внутри проверочного проекта, удалится вместе с ним, а архивация в T3
   файлы не сохраняет.
2. Закоммить отчёт и свидетельства в постоянном репозитории и убедись, что они читаются по
   своему постоянному пути. Пока это не выполнено, каталог не удаляется: незакоммиченный
   отчёт можно потерять при обычной работе над постоянным репозиторием.
3. Сверь цель: удаляется абсолютный путь, записанный в отчёте; `git rev-parse HEAD` в цели
   должен вернуть полный SHA из `git.head` результата применения (`git.commit` содержит
   сокращённые 12 символов, `git log --oneline -1` печатает сокращённый хеш, а заголовок
   коммита у разных прогонов одинаковый — сверять по ним нельзя); `git status --porcelain --ignored`
   пуст. Артефакты прогона внутри цели (логи, временные файлы) удали или зафиксируй до
   сверки: пустое дерево — условие классификации, а не повод оставить каталог. Другой SHA,
   непустой список или иной путь означают чужой проект — не удаляй, причину опиши в отчёте.
   Символическую ссылку не разыменовывай: удаляется сама ссылка, а не каталог, в который
   она ведёт.
4. Архивируй потоки и регистрацию проекта в T3; удаление каталога регистрацию не отменяет.
5. Удали каталог и проверь, что путь отсутствует.

Если прогон выполнялся на реальном каталоге пользователя, удаление не применяется: такой
проект живёт по обычным правилам, а не как проверочный.

## 6. Отказы и ограничения

- Каталог не пуст → `Greenfield requires a new project`. Используй `install --mode existing`
  или новый каталог; не удаляй чужие файлы ради установки.
- Конфликт каркаса (например, другой `README.md`) → применение блокируется целиком.
- Повторный запуск на установленном проекте → `AEK already installed; use upgrade`.
- Нет `git` или не настроена личность коммита → проект создан, но `git.error` заполнен,
  `checks.git` и `passed` равны `false`, код возврата 2, причина в `warnings`. Это не
  повод переписывать чужую историю: настрой identity и заверши коммит вручную или
  через `upgrade`/`doctor`.
- Сбой применения после установки кита оставляет полусостояние: повторный `new-project`
  ответит `AEK already installed; use upgrade`. Заверши установку через `upgrade`,
  создай недостающий каркас вручную и проверь `doctor`; молчаливого отката нет.
- Сеть нужна только для получения источника и последующих действий по брифу; сам
  `new-project` сетевых запросов не делает, токенов не читает и не логирует.
- Расписание, CI, деплой, публикация и push не выполняются: это отдельные поручения.
