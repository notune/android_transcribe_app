# Knowledge Management в Agentic Engineering Kit

## Границы ответственности

- **AEK:** методология, роли, диалог, параллелизм, безопасность и Quality Gates.
- **OpenSpec:** согласованные текущие требования и история изменений поведения продукта.
- **Markdown docs/:** подтверждаемые знания о системе: решения, ограничения, устройство компонентов, эксплуатационные инструкции.
- **OntoShip GitMark:** производная поисковая база SQLite и проверка связности Markdown. Не отдельный источник истины.

Ни OntoShip `dev-flow`, ни `/ship`, ни альтернативные правила веток и выпуска **не подключаются**.

## Зачем нужен пакет навыков

При росте кодовой базы агенты вновь исследуют уже известные решения, теряют контекст между сессиями и могут опираться на устаревшие документы. `kb-search` сначала находит релевантные записи; `kb-curate` поддерживает качество; `kb-audit` отслеживает устаревание, дублирование и связи.

Сильный принцип: **поиск → проверка источника → изменение по OpenSpec → подтверждение → обновление знания**.

## Формат новых документов

Документы проекта остаются обычными Markdown-файлами. Для значимых новых записей можно использовать облегчённую YAML-шапку:

```yaml
---
node_type: decision
title: Rate-limit API
description: Почему выбрали существующий rate limiter вместо самописного
status: active
updated: 2026-11-12
links:
  documents: [../../src/api/limits.py]
---
```

Для подтверждённых знаний: `verified` только после реального review, а не по самоотчёту агента. Для генерированных: `generated` с фактическим источником. Для потенциально устаревающих фактов: `stale_after` если определён срок ревизии.

**OpenSpec не переоформляем в онтологию OntoShip.** При противоречиях OpenSpec о согласованном поведении имеет приоритет; код и тесты могут показать расхождение, которое нужно решить, а не молча исправить документ.

## Облегчённая установка и безопасность

Пакет навыков отключён по умолчанию. AEK копирует только собственные инструкции. Для GitMark используется отдельная команда с явным сетевым разрешением и проверкой привязанного blob SHA. Индекс `.gitmark/index.db` в `.gitignore`, а `.agentic-kit` и `.agents/skills` в `.gitmarkignore` по согласованию. Не добавляй исключения автоматически к существующему файлу.

Проверяй, что локальные данные и HTML-карты не передаются в публичные каналы. Инструмент может читать все не исключённые Markdown-документы, поэтому проектные права и область индексации важны.

## Brownfield

- Сначала инвентаризация и read-only аудит.
- Затем исходный `lint/health` baseline и список противоречий.
- После согласования документировать только изменяемые или действительно важные модули.
- Не заставлять все старые файлы проходить строгую онтологию.
- Для параллельного восстановления документов использовать AEK Swarm, не сторонний dev-flow.

## Пилот и критерий полезности

По одному существующему проекту выбрать 20–30 вопросов и 3–5 задач передачи контекста между агентами. В одинаковых условиях сравнить grep/обычный поиск и GitMark с проверкой результата по оригинальным файлам:

- hit@1 / hit@5 и правильность окончательного ответа;
- время до достоверного ответа, число прочитанных документов, расход токенов;
- время передачи работы другому харнессу без повторного интервью;
- качество новых знаний, количество расхождений и риск контекстных ошибок.

Если локальной пользы нет, оставить пакет навыков необязательным или не использовать его вовсе.
