# Product Design: Design Before Code

Для продукта с пользовательским интерфейсом Product Designer совместно с PM/BA прорабатывает сценарии, навигацию, wireframes, ключевые состояния, адаптивность и доступность, затем визуальную систему и проверяемый прототип. Согласует существенные решения до основной реализации.

Приоритет готовых компонентных библиотек, но решение учитывает сопровождаемость: пакет с обновлениями и скопированный код компонентов имеют разные расходы.

Артефакты могут быть компактными: ссылка на макет/прототип + карта сценариев + критерии приёмки. Не создавай тяжёлую дизайн-систему для одного экрана.

При включённом профиле `Web Development` дизайнер, архитектор и фронтенд-разработчик используют `aek-modern-web-guidance` для выбора современных браузерных API, форм, доступных компонентов, адаптивных паттернов и fallback. Это дополняет, но не заменяет дизайн-систему, макеты и визуальную приёмку. Внешний CLI — только после разрешения на загрузку.

Visual QA: соответствие утверждённому макету, desktop/mobile, loading/error/empty, клавиатура, контраст, фокус, WCAG 2.2 AA для веб-целей; скриншоты и результаты E2E. Автоматическая проверка доступности не заменяет ручную.

## Проверяемое поведение интерфейса

Для нового или существенно изменяемого интерактивного компонента дизайнер и разработчик до реализации согласуют краткие критерии поведения. Для простого статического экрана отдельный документ не нужен, достаточно применимых критериев в OpenSpec или задаче.

- **Действия и состояния:** что человек выбирает, подтверждает и отменяет; что происходит при загрузке, ошибке, пустых результатах и отключённых действиях.
- **Клавиатура:** порядок Tab, работа стрелок, Enter, Space, Escape и других клавиш по назначению компонента. Используй применимые образцы WAI-ARIA APG.
- **Фокус:** начальная точка при открытии, переходы между частями, возврат к инициатору после закрытия, реакция на ошибку. Все необходимые действия должны быть доступны без мыши.
- **Доступность:** однозначные названия полей и кнопок, связи подписей и ошибок, роли и состояния ARIA, объявления важных изменений для программ чтения с экрана.
- **Среда:** поддерживаемые браузеры, адаптивность, сенсорный ввод, серверная разметка и последующая загрузка JavaScript, направление текста справа налево при необходимости.

Сначала используй принятую библиотеку компонентов. Не заменяй её и не вводи зависимость ради такого перечня без сравнения и согласования.

### Рекомендуемая основа новых React-продуктов

Для **новых** веб-приложений на React исходный кандидат: [shadcn/ui](https://ui.shadcn.com) с [Base UI](https://base-ui.com) и [Tailwind CSS](https://tailwindcss.com). Это предпочтение для проектирования и реализации, а не универсальная обязательная зависимость. До установки согласуй React/TypeScript, требования к оформлению, дизайн-токены, компоненты, доступность, совместимость и стоимость сопровождения.

Работа с shadcn/ui подразумевает добавление копий исходного кода компонентов в продукт. Проект становится ответственным за их поддержку, безопасность, обновление и сохранение собственных изменений. Для нового приложения Base UI является рекомендуемой основой; не меняй существующую систему на Radix или Base UI автоматически. Для внутренних панелей с большим количеством готовых форм и элементов рассмотрите Mantine как альтернативу.

Прежде чем писать код: согласуй основную навигацию, состояния, темы, цвета, типографику, ширину, адаптивность и прототип. Далее используй выбранную библиотеку, проверяй реальную клавиатурную доступность и итоговый вид в браузере. Не подменяй визуальную приёмку демонстрационными скриншотами библиотеки.

## Проверка взаимодействий

QA проверяет клавиатуру, фокус, открытие и закрытие окон, отмену, подписи, ошибки, доступность и затронутые браузеры. Проверки DOM и ARIA не заменяют испытаний в настоящем браузере, особенно для фокуса, всплывающих элементов, расположения и контраста.

Значимые новые тесты по возможности проверяй на способность обнаруживать неисправность: в изолированной тестовой среде и с разрешения временно нарушь поведение, убедись, что тест не проходит, затем восстанови код. Не делай это в рабочей среде. Фиксируй, что проверено и что осталось непроверенным.

## Интерфейс для ИИ-агента, только если он нужен продукту

Если продукт должен позволять ИИ-агенту пользоваться интерфейсом, отдельно определи допустимые действия и данные. Для каждого поля и действия нужны понятные и различимые названия. Секреты не должны раскрываться агенту; денежные, необратимые и другие значимые действия требуют подтверждения уполномоченного человека.

Клиентские атрибуты и проверки не являются границей безопасности. **Проверку полномочий, входных данных и прав на действие выполняет сервер.** Предусмотри отказ, проверку результата и журналирование значимых операций. Подключение WebMCP и подобных механизмов требует отдельного анализа угроз и разрешения.

В качестве необязательного кандидата можно рассмотреть [Vercel UI SDK](https://github.com/vercel-labs/ui) с механизмами `createAgent`, `snapshot()`, `act()` и `allow`. На момент обзора библиотека имеет статус beta и требует проверки совместимости. Она не входит в обязательный набор AEK и не устанавливается автоматически.
