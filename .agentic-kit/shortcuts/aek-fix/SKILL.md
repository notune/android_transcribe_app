# /aek_fix

Выполняй по запросу пользователя. Используй текущий корень проекта и его действующие инструкции. Для установленного AEK прочитай `.agentic-kit/AGENTS.md` и применимые разделы `.agentic-kit/docs/DAILY_WORKFLOW.md`, `docs/WORKFLOW.md`, `docs/PROCESSES.md` и `docs/CLI.md` внутри кита. Если AEK не установлен, не выдумывай локальные команды: предложи `/aek_greenfield` или `/aek_brownfield`.

Учитывай уже согласованный объём и разрешения. Повторное согласование нужно только при изменении плана, области влияния или существенных решений. Не публикуй выпуск и не меняй внешние системы без соответствующего поручения. Результаты проверок и непроверенные пункты сообщай отдельно.


Перед работой восстанови или сохрани `execution_boundary` по docs/PROCESSES.md. Новая задача по умолчанию ограничена verification; явный другой предел передай через `--stop-after`, с источником пользовательского поручения там, где он требуется. После завершения разрешённого этапа сохрани контекст и останови продвижение. Успешный verify и самостоятельно созданный release-approval не разрешают release/done за пределами поручения. Старую открытую задачу без границы сначала явно мигрируй командой `boundary` на основании действующего согласования.

1. Используй существующую задачу либо создай `new-task --process fix` с профилем по риску и UI/HTTP при применимости. Зафиксируй ожидаемое и фактическое поведение. Существующий процесс продолжай по закреплённому определению; задачу без процесса после discovery веди через обычные `record`/`advance`.
2. Воспроизведи дефект и локализуй причину. Если воспроизведение невозможно, сообщи, что именно неизвестно, не выдавай предположение за диагноз. В planning сохрани подтверждённую причину как `record --key root_cause --file FILE`.
3. Для каждого шага процесса выполняй `process start-step`, работу и `record`, `process finish-step --outcome passed`, затем `advance --to NEXT_STAGE`. Указывай текущий `--step STAGE`. Дополнительные доказательства fix не заменяют обычные условия профиля из docs/WORKFLOW.md.
4. Выполни исправление причины. Добавь регрессионную проверку для подтверждённого дефекта и проверь соседние состояния. Зарегистрируй подтверждение реализации, закончи implementation и перейди в verification; начни этот шаг.
5. Выполни принимаемые проверки через `record --run` на просмотренном коммите с чистым рабочим деревом. Сохрани сценарий и ссылки на реальные результаты как `record --key regression_check --file FILE`. Запуск с `--allow-dirty --reason TEXT` только диагностический. Закончи verification через `finish-step` и вызови `verify`. Если verification уже passed и тесты запущены снова, используй `process refresh-step --step verification --reason TEXT` перед `verify`.
6. При неуспехе отметь исход running-шага через `process finish-step --outcome failed --reason TEXT` и `transition --state failed --reason TEXT`. Для исправления кода вернись на implementation через явную доработку по docs/PROCESSES.md. Повтор шага ограничен и не заменяет согласование нового объёма. Обнови owner, branch, worktree, summary, next_action и blockers через `context --file`. Сообщи причину, изменение, результаты и ограничения.
