# /aek_resume

Выполняй по запросу пользователя. Используй текущий корень проекта и его действующие инструкции. Для установленного AEK прочитай `.agentic-kit/AGENTS.md` и применимые разделы `.agentic-kit/docs/DAILY_WORKFLOW.md` и `docs/PROCESSES.md` внутри кита. Если AEK не установлен, не выдумывай локальные команды: предложи `/aek_greenfield` или `/aek_brownfield`.

Учитывай уже согласованный объём и разрешения. Повторное согласование нужно только при изменении плана, области влияния или существенных решений. Не публикуй выпуск и не меняй внешние системы без соответствующего поручения. Результаты проверок и непроверенные пункты сообщай отдельно.


Перед работой восстанови или сохрани `execution_boundary` по docs/PROCESSES.md. Новая задача по умолчанию ограничена verification; явный другой предел передай через `--stop-after`, с источником пользовательского поручения там, где он требуется. После завершения разрешённого этапа сохрани контекст и останови продвижение. Успешный verify и самостоятельно созданный release-approval не разрешают release/done за пределами поручения. Старую открытую задачу без границы сначала явно мигрируй командой `boundary` на основании действующего согласования.

1. Если ID неизвестен, выполни `list-tasks --target PROJECT`. Для выбранной задачи выполни `python3 .agentic-kit/tools/aek.py resume --target PROJECT --task ID`.
2. Прочитай требования, решения, события и изменённые файлы. Восстанови owner, branch, worktree, scope, summary, next_action, blockers и последнюю попытку; сверь их с фактическим Git и доказательствами. История чата не заменяет состояние проекта.
3. Для процесса продолжай сохранённое определение и текущий шаг. При definition_changed не подменяй процесс новым. Running-шаг после прерывания сначала проверь по фактическим результатам; не начинай вторую попытку и не считай незавершённую проверку успешной. Задачу без процесса после discovery продолжай обычным workflow.
4. Для blocked/failed/rework сначала разреши причину, обнови context.blockers и выполни допустимый `transition` из docs/DAILY_WORKFLOW.md. Затем blocked-шаг продолжай через `process resume-step`, failed-шаг повторяй через `process retry` и новый `start-step` только в пределах лимита. Для изменения кода на уже пройденном этапе используй явный rework по docs/PROCESSES.md.
5. Продолжи разрешённую работу: `start-step → record → finish-step → advance`. Если verification уже passed и повторён реальный запуск тестов, используй `refresh-step` перед `verify`. Обнови контекст и следующий шаг через `context --file`. `resume` сам состояние не меняет; отменённую или завершённую задачу молча не открывай.
6. Не запрашивай повторно действующие согласования. Уже записанное допустимое исключение требует явного `--allow-waiver` в применимых командах; этот флаг не заменяет согласование и не включается автоматически для CI.
