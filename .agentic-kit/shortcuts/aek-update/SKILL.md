# /aek_update

Выполняй по запросу пользователя. Используй текущий корень проекта и его действующие инструкции. Для установленного AEK прочитай `.agentic-kit/AGENTS.md` и применимые разделы `.agentic-kit/docs/DAILY_WORKFLOW.md` и `docs/PROCESSES.md` внутри кита. Если AEK не установлен, не выдумывай локальные команды: предложи `/aek_greenfield` или `/aek_brownfield`.

Учитывай уже согласованный объём и разрешения. Повторное согласование нужно только при изменении плана, области влияния или существенных решений. Не публикуй выпуск и не меняй внешние системы без соответствующего поручения. Результаты проверок и непроверенные пункты сообщай отдельно.


Перед работой восстанови или сохрани `execution_boundary` по docs/PROCESSES.md. Новая задача по умолчанию ограничена verification; явный другой предел передай через `--stop-after`, с источником пользовательского поручения там, где он требуется. После завершения разрешённого этапа сохрани контекст и останови продвижение. Успешный verify и самостоятельно созданный release-approval не разрешают release/done за пределами поручения. Старую открытую задачу без границы сначала явно мигрируй командой `boundary` на основании действующего согласования.

1. Проверь установленный AEK, реестр компонентов и текущие пользовательские изменения. Получи новый проверенный источник AEK отдельно от проекта, запиши SHA и VERSION. Прочитай docs/COMPONENTS.md, docs/UPGRADE.md и docs/PROCESSES.md.
2. Создай задачу обновления через `new-task --process update` с профилем по риску либо продолжи существующую. Если установленный контроллер ещё не поддерживает процессы, используй его обычный workflow и журнал обновления; не вызывай отсутствующие команды. Существующей задаче после discovery не присоединяй процесс задним числом. Обновление кита не заменяет закреплённое определение уже начатого процесса.
3. При наличии процесса на каждом этапе соблюдай `process start-step → record → process finish-step --outcome passed → advance`. В discovery сохрани `environment_inventory`; в planning сохрани `update_plan` и `recovery_plan`. Условия выбранного профиля также обязательны.
4. Для зарегистрированных компонентов проверь официальные версии и совместимость через уже доступные источники. Подготовь файл кандидатов по схеме docs/COMPONENTS.md. Не используй плавающий latest при применении; не добавляй незарегистрированные инструменты автоматически.
5. Из нового источника выполни `python3 tools/aek.py update --target PROJECT`, при наличии проверенных кандидатов добавь `--candidates FILE`, для выбранных компонентов `--component ID`. Покажи единый план, конфликты, версии, область влияния, доступность отката и plan_id. Сохрани точный план и восстановление до завершения planning.
6. В implementation примени согласованный неизменившийся план с `--apply --plan-id ID`. При ранее выданном разрешении на этот план не спрашивай повторно. Глобальные инструменты затрагивают другие проекты; это должно быть видно до применения. Сохрани `update_result` со ссылками на настоящий журнал, идентификаторы запусков и резервных копий; затем закончи шаг и перейди к verification.
7. Проверь результаты всех компонентов и сохрани `environment_check`, выполни обязательные реальные проверки профиля. Закончи verification и вызови `verify`. При частичном сбое не объявляй общее обновление успешным: зафиксируй failed/blocked, журнал и команды восстановления. У update нет повторных попыток шага; сначала разбор журнала и новый точный план, затем явная доработка. Сохрани контекст и следующий шаг через `context --file`, если установленный контроллер поддерживает эту команду.
8. Команда обновляет окружение AEK. Требования и код приложения меняются через `/aek_change`, зависимости приложения без отдельного включения в управление не обновляются.
