# /aek_verify

Выполняй по запросу пользователя. Используй текущий корень проекта и его действующие инструкции. Для установленного AEK прочитай `.agentic-kit/AGENTS.md` и применимые разделы `.agentic-kit/docs/DAILY_WORKFLOW.md` и `docs/PROCESSES.md` внутри кита. Если AEK не установлен, не выдумывай локальные команды: предложи `/aek_greenfield` или `/aek_brownfield`.

Учитывай уже согласованный объём и разрешения. Повторное согласование нужно только при изменении плана, области влияния или существенных решений. Не публикуй выпуск и не меняй внешние системы без соответствующего поручения. Результаты проверок и непроверенные пункты сообщай отдельно.

1. Прочитай критерии приёмки. Сверь `status`, профиль, UI/HTTP, текущий коммит и локальные изменения. Финальная проверка требует verification или release, активной задачи и отсутствия context.blockers. Не перескакивай непройденные этапы ради запуска verify. Терминальная задача требует новой связанной задачи.
2. Если у задачи есть процесс, проверь его состояние. Для первого pending verification на текущем этапе выполни `process start-step --step verification`; для running продолжай ту же попытку. Для failed/blocked сначала устрани причину и используй разрешённый retry/resume-step по docs/PROCESSES.md. Не переводи такие шаги в passed автоматически. Если процесса нет, используй обычные record и verify.
3. Выполни применимые согласованные команды через `record --run` на чистом просмотренном коммите. Для UI нужны действительные свидетельства браузерной проверки; недоступность инструмента не равна успеху. Диагностический `--allow-dirty` приёмку не проходит. Если требуется заменить уже подтверждённые документы или visual_qa, используй явную доработку до записи нового результата: refresh-step допускает замену только выполненных tests/runtime_smoke.
4. После успешных проверок для running verification зарегистрируй также все обязательные документы профиля и процесса (включая regression_check для fix), затем выполни `process finish-step --step verification --outcome passed`. Для уже passed verification после повторного запуска tests/runtime_smoke используй `process refresh-step --step verification --reason TEXT`. Это повторная проверка доказательств, а не обход условий или новый запуск шага.
5. Выполни `python3 .agentic-kit/tools/aek.py verify --target PROJECT --task ID` с необходимыми требованиями проекта. Сам verify тесты не запускает. Уже согласованное исключение учитывается только при явном --allow-waiver в применимых командах; CI по умолчанию его не принимает.
6. Не ослабляй профиль и не подменяй проверку успешной заглушкой. При ошибке сохрани причину и состояние failed; если шаг ещё running, зафиксируй его неуспешный исход до остановки задачи. Перечисли подтверждённое и непроверенное отдельно, сохрани препятствия и следующий шаг.
