# /aek_change

Выполняй по запросу пользователя. Используй текущий корень проекта и его действующие инструкции. Для установленного AEK прочитай `.agentic-kit/AGENTS.md` и применимые разделы `.agentic-kit/docs/DAILY_WORKFLOW.md`, `docs/WORKFLOW.md`, `docs/PROCESSES.md` и `docs/CLI.md` внутри кита. Если AEK не установлен, не выдумывай локальные команды: предложи `/aek_greenfield` или `/aek_brownfield`.

Учитывай уже согласованный объём и разрешения. Повторное согласование нужно только при изменении плана, области влияния или существенных решений. Не публикуй выпуск и не меняй внешние системы без соответствующего поручения. Результаты проверок и непроверенные пункты сообщай отдельно.


Перед работой восстанови или сохрани `execution_boundary` по docs/PROCESSES.md. Новая задача по умолчанию ограничена verification; явный другой предел передай через `--stop-after`, с источником пользовательского поручения там, где он требуется. После завершения разрешённого этапа сохрани контекст и останови продвижение. Успешный verify и самостоятельно созданный release-approval не разрешают release/done за пределами поручения. Старую открытую задачу без границы сначала явно мигрируй командой `boundary` на основании действующего согласования.

1. Проверь текущую задачу и существующие требования; уточни только отсутствующие критерии результата. Восстанови владельца, ветку, worktree, область, препятствия и следующий шаг через `resume`.
2. Для новой задачи выбери lite/standard/critical по риску, укажи UI и HTTP при применимости и создай `aek.py new-task --process change`. Существующую задачу продолжи с её закреплённым процессом. Если у неё нет процесса и уже пройден discovery, используй обычные `record`/`advance`, не присоединяй процесс задним числом.
3. Сохрани согласованный объём, найди переиспользуемый код, проверь архитектуру и неявные состояния. Для существенного UI согласуй дизайн до реализации.
4. Для каждого шага процесса выполняй `process start-step --step STAGE`, работу и `record`, затем `process finish-step --step STAGE --outcome passed` и только после него `advance --to NEXT_STAGE`. Зарегистрируй все применимые основания профиля через `record --file` по docs/WORKFLOW.md. Ни запись доказательства, ни завершение шага этап не меняют.
5. Выполни изменение в согласованной области. Зарегистрируй фактическое подтверждение реализации, закончи implementation и перейди в verification. Начни шаг verification до итоговых проверок.
6. Для принимаемых проверок нужен просмотренный коммит и чистое рабочее дерево. Выполни согласованные проверки через `record --run`, закончи verification через `finish-step`, затем вызови `verify`. Запуски с `--allow-dirty --reason TEXT` только диагностические. Для повторного реального запуска после уже passed verification используй `process refresh-step --step verification --reason TEXT` перед `verify`.
7. Сохрани контекст и следующий шаг через `context --file`. При препятствии или провале отметь исход running-шага и `transition --state blocked|failed --reason TEXT`. Продолжай только после устранения препятствий; повтор и доработка описаны в docs/PROCESSES.md, автоматические бесконечные повторы запрещены. Сообщи результат, проверки и непроверенное. Публикация не подразумевается.
