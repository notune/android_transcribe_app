# Agentic Engineering Kit — инструкции всем агентам

**Пути в этом документе указаны относительно каталога, где находится данный AGENTS.md.** При установке в проект это `.agentic-kit/`.

1. До действий изучи `docs/PRINCIPLES.md`, `docs/METHODOLOGY.md`, применимую роль в `roles/`, текущие требования и состояние задачи. Не считай историю чата единственным источником истины.
2. При создании или развитии продукта сначала проведи диалог с пользователем о цели, ограничениях и критериях приёмки. Не начинай существенную разработку без согласования требований.
3. **Reuse → Research → Build**: сначала ищи уже существующий код, затем зрелые библиотеки, и только затем создавай свой. Исправляй первопричину, не маскируй симптомы.
4. Проверяй официальные источники, фактические API и запускаемые тесты. Явно называй существенные допущения; не выдавай их за факты.
5. Для UI: **Design Before Code**, согласование прототипа, после реализации Visual QA. Применяй готовые дизайн-системы.
6. **Secure by Design**: минимальные права, защита секретов, границы данных, зависимости, анализ угроз. Опасные и продуктивные действия требуют разрешения.
7. **Architecture Simplification Gate**: что можно не делать, переиспользовать, упростить? Не вводи компоненты на будущее.
8. **Swarm Planning Gate**: перед существенной реализацией проверь DAG зависимостей; параллель независимые задачи в допустимых пределах. Разделяй рабочие области и ресурсы; интегрируй через одного ответственного.
9. Перед началом нового или существующего проекта используй `skills/harness-discovery-assignment/SKILL.md`: сначала обнаружь харнессы, затем уточни только неизвестные ограничения пользователя, оцени подтверждённые модели/effort, предложи primary и fallback по ролям, получи согласование существенных провайдеров/передачи данных и зафиксируй `routes_confirmed`. Не путай наличие CLI с проверенной моделью или разрешением пользователя. Внешние скиллы проверяй до установки.
10. Не меняй самостоятельно утверждённый процесс. Сохраняй подтверждающие артефакты; явно фиксируй исключения. Локальный чекер — помощь, не доказательство полномочий пользователя.
11. При работе с кодом ищи неявные машины состояний в затронутых участках, улучшай **UX, DX и AX** без нарушения контрактов. Не обещай отсутствие регрессий без тестирования.
12. В конце разделяй «реализовано», «фактически проверено», «не проверено», «риски». Не сообщай об успешных проверках, которых не было.
13. При подготовке выпуска соблюдай `docs/VERSIONING.md`: отличай коммит и принятый этап от версии продукта, согласуй номер и совместимость, сверь результаты приёмки, сборку и точный коммит. Теги, GitHub Releases и развёртывание выполняй только с отдельным разрешением.

14. Для задач `standard`, `critical` и существенных UI-изменений **до реализации** создавай задачу через `aek.py new-task`. До назначения проверяющих сохрани маршрут исполнителя через `execution route`: проверяющий не может идти тем же провайдером. Выполняй согласованные проверки через `record --run`; не выдавай наличие файла с хешем за факт запуска теста. Перед готовностью запускай `aek.py verify` и проверяй точный Git-коммит. Реальная независимая блокировка требует защищённого CI. Проверяющему передавай задание по `templates/REVIEW_BRIEF.md`; новые назначения требуют отчёт схемы 2, где открытая находка `important` блокирует `approved`.
15. Для UI до проектирования выясни, доступен ли браузер, а до завершения выполни реальную Visual QA. Отсутствие доступа, падение теста или неактуальные доказательства означает «не проверено», а не «готово». Исключения возможны только с явным согласием пользователя и никогда не превращают неуспешный тест в успешный.
16. Для нового React-продукта по умолчанию **предложи** shadcn/ui + Base UI + Tailwind CSS. Выбор и установка только после проверки требований и согласования. Существующие библиотеки компонентов автоматически не заменяй. Для проверки через агентские инструменты предпочитай Playwright MCP, для диагностики Chrome DevTools MCP, для среды без MCP Playwright CLI; в CI используй реальные Playwright Test по необходимости.

## Язык и оформление

Это правило действует для ответов пользователю, требований, отчётов, документации и других текстов, которые создают агенты, если пользователь не попросил использовать другой язык.

- Пиши понятным русским языком, используй минимум иностранных слов.
- Не заменяй обычные русские слова иностранными ради стиля.
- Редкий или узкоспециальный термин объясняй при первом употреблении.
- Имена команд, файлов, программных интерфейсов, идентификаторов и полей кода оставляй без перевода.
- Не используй длинное тире. Перестраивай предложение, используй точку, запятую или двоеточие.

Для мелкой правки выбирай облегчённый процесс, но не пропускай обязательные требования безопасности и корректности.

17. Сохраняй конечный этап поручения в `execution_boundary` по docs/PROCESSES.md. У новой задачи по умолчанию предел verification. На границе заверши разрешённый шаг, проверки и передачу контекста; не переходи к release/done без действующего разрешения на расширение. Собственный отчёт и файл release-approval не являются согласием пользователя. При возобновлении сначала восстанови эту границу.
